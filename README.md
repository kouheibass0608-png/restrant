# TableCheck 空席ウォッチャー

[ガストロノミー "ジョエル・ロブション"](https://www.tablecheck.com/ja/shops/joelrobuchon/reserve)
(恵比寿ガーデンプレイス) の TableCheck 予約枠を定期的にチェックし、
**空席が出たらスマホにプッシュ通知**を送るツールです。

- チェックは **GitHub Actions** が5分ごとに自動実行 (PC不要)
- 通知は **[ntfy](https://ntfy.sh/)** で受信 (無料・アカウント登録不要)
- 通知をタップするとそのまま TableCheck の予約ページが開きます

## 仕組み

```
GitHub Actions (毎時起動 → ジョブ内で5分ごとにチェック)
  └─ tablecheck_watcher
       ├─ TableCheck の予約ページが使う内部API
       │    GET /ja/shops/joelrobuchon/available/timetable
       │  を週単位でページングし、今後60日分の空き枠を取得
       │  (監視する人数ごとに別々に問い合わせる)
       ├─ 前回チェック時の状態 (state.json) と比較して「新たに空いた枠」を検出
       └─ 新たな空きがあれば ntfy にプッシュ通知
            (state.json はリポジトリにコミットして次回に引き継ぐ)
```

- 通知が来るのは「前回チェック時になかった空きが出たとき」だけです (毎回は来ません)
- 人数ごとに独立して判定します。例えば2名の空きが無いままでも、3名の空きが出れば通知します
- ⚠️ **この店は2〜4名のみ予約可能です。`num_people` に1を入れないでください** —
  タイムテーブルAPIは1名でも空きを返しますが、実際には予約できないため通知がすべて無駄になります
  (詳細は下記「1名を監視してはいけない理由」)
- チェックの失敗が続いた場合 (サイト仕様変更など) は、一度だけ警告通知が届きます

## セットアップ

### 1. ntfy アプリを入れて購読する

1. スマホに ntfy アプリをインストール
   ([iOS](https://apps.apple.com/us/app/ntfy/id1625396347) /
   [Android](https://play.google.com/store/apps/details?id=io.heckel.ntfy))
2. アプリで **Subscribe to topic** を選び、**推測されにくいトピック名**を購読する
   - 例: `robuchon-aki-x7k2m9`
   - ⚠️ ntfy.sh のトピックは名前を知っていれば誰でも購読/送信できます。
     必ずランダムな文字列を含めてください。

### 2. GitHub Secrets にトピック名を設定する

リポジトリの **Settings → Secrets and variables → Actions → New repository secret** で:

| Name | Value |
|---|---|
| `NTFY_TOPIC` | 手順1で決めたトピック名 (例: `robuchon-aki-x7k2m9`) |

(セルフホストの認証付き ntfy サーバーを使う場合のみ `NTFY_TOKEN` も設定)

### 3. main ブランチにマージする

定期実行 (cron) は **main ブランチのワークフローだけ**が対象です。
この変更を main にマージした時点から10分ごとのチェックが始まります
(実行時間の無料枠の都合上、リポジトリは public にしてください。下記参照)。

### 4. 動作確認

**Actions → check-availability → Run workflow** から手動実行できます:

| mode | 動作 |
|---|---|
| `test-notify` | テスト通知を送る (ntfy の設定確認) |
| `dry-run` | 空き状況を取得してログに表示するだけ (通知しない) |
| `check` | 本番と同じ動作 (初回は「監視開始」通知が届きます) |

まず `test-notify` でスマホに通知が届くことを確認してください。

## 設定の変更 (`config.toml`)

```toml
[search]
num_people = [2]     # 監視する人数 (複数指定可。この店は2〜4名のみ予約可)
days_ahead = 60      # 何日先まで監視するか
time_ranges = []     # 空 = 全時間帯。ディナーのみなら ["17:00-22:00"]
dates = []           # 特定日だけ監視: ["2026-09-15", "2026-09-22"]
```

変更を main に push すれば次回チェックから反映されます。

- 監視間隔は `.github/workflows/check.yml` の `cron` で変更できます。
- この店舗の予約枠 (2名の場合、2026-08 実測):
  - **平日**: ディナーのみ 16:30〜19:30 開始 (30分刻み・7枠)
  - **土日**: 上記に加えてランチ 11:00〜12:30 開始 (30分刻み・4枠)

## OMAKASE (omakase.in) は監視できません

カンテサンスなど OMAKASE 掲載店の監視を検討しましたが、**技術的に不可能**という結論です。

OMAKASE は **Cloudflare のボット対策**の内側にあり、プログラムからのアクセスは
ページを読む前に遮断されます (2026-08 実測):

```
HTTP 403
title: Just a moment...        ← Cloudflare のボットチャレンジ画面
```

`scripts/probe_omakase.py` で店舗ページと候補エンドポイントを一通り試しましたが、
いずれも 403 でした。これは店舗側/サイト側が**意図的に設置したアクセス制御**です。
回避する実装 (ヘッドレスブラウザでのチャレンジ突破など) は行いません。

### 代わりの手段: OMAKASE 公式の通知をプッシュに変換する

OMAKASE にはキャンセル発生時にメールで通知する公式機能があります。
これを ntfy のメール投稿機能と組み合わせると、**コードなし**で
スマホへのプッシュ通知にできます。

1. OMAKASE にログインし、対象店舗を「お気に入り」に登録する
2. メールアプリ (Gmail など) で、OMAKASE からのメールを
   `<あなたのntfyトピック>@ntfy.sh` に自動転送するフィルタを作る
3. キャンセル通知メールが、そのままスマホのプッシュ通知になる

Gmail の自動転送は初回に確認コードの入力を求められますが、
そのコード自体も ntfy の通知として届くので、そこから確認できます。

## 1名を監視してはいけない理由

`num_people` に 1 を指定すると、大量の「空き」が検出されますが**そのすべてが予約できません**。

- 予約ページの人数セレクタの選択肢は **2・3・4 のみ**(1 は存在しない)
- タイムテーブルAPIは `num_people_adult=1` を受け付け、席の空きをそのまま返してしまう
- しかし実際に予約しようとすると、サーバーが次のように拒否する:

  ```
  {"status":"invalid","data":"ご予約人数は2以上の値にしてください"}
  ```

2026-08 時点の実測では、1名だと60日間で122枠が「空き」と返る一方、2〜4名はいずれも0枠でした。
この122枠はすべて予約不可です。

同じ罠は他の店舗にもあり得ます。監視人数を追加する際は、
**予約ページの人数セレクタにその人数の選択肢があるか**を必ず確認してください。
`scripts/probe_api.py` を実行すると、セレクタの選択肢と実際の予約可否を確認できます。

## 実行間隔のしくみ

**cron を短くしても間隔は詰まりません。** GitHub の定期実行は混雑時に大きく遅延し、
`*/10`(10分間隔)を指定した際の実測は次のとおりでした。

| 指定 | 実際の発火間隔 |
|---|---|
| `*/10 * * * *` | 平均 **約1時間**(最短26分・最長2時間18分) |

そのため cron は**毎時1回**だけにし、**1回の実行の中でループして5分ごとにチェック**
しています。これが実質的な監視間隔になります。

```
cron (毎時) → ジョブ起動 → [チェック → 5分待機] を約110分ぶん繰り返す
                              ↑ 次回の起動が遅延しても途切れないよう、
                                cron 周期より長くループする
```

発火が重なった時点で `concurrency` により古い実行が新しい実行に置き換わるため、
二重にチェックされることはありません。

調整するには `.github/workflows/check.yml` の以下を変更します:

| 変数 | 既定値 | 意味 |
|---|---|---|
| `CHECK_INTERVAL` | `300` | チェック間隔(秒) |
| `LOOP_MINUTES` | `110` | 1回の実行がチェックを続ける時間(分) |

### public リポジトリであることが前提です

この方式はランナーをほぼ常時占有するため、**実行時間が無制限の public リポジトリ**でのみ
成立します。private の無料枠(月2,000分)ではまったく足りません。

**private に戻す場合は**、`schedule` を `- cron: "*/30 * * * *"` に変え、
`Watch (loop)` ステップを使わない構成(1回チェックして終了)に戻してください。

### その他

- ntfy のトピック名は Secrets に保存されるため、public にしても公開されません
  (実行ログでも `***` に伏せられます)。
- `state.json` は空き状況が変化したときだけコミットされます。変化がない場合も
  週1回だけ更新し、リポジトリの活動を保ちます
  (public リポジトリは60日間活動がないと定期実行が自動停止されるため)。
- TableCheck への問い合わせは 1チェックあたり約9リクエスト
  (60日ぶんを週単位で取得)、5分間隔で **約108リクエスト/時** です。
  リクエスト間には1秒の待機を入れています。

## ローカルでの実行

Python 3.11 以上があれば依存パッケージなしで動きます:

```bash
# 空き状況を見るだけ
python -m tablecheck_watcher check --dry-run

# 通知テスト
NTFY_TOPIC=あなたのトピック python -m tablecheck_watcher test-notify

# 本番と同じ動作 (state.json を読み書き)
NTFY_TOPIC=あなたのトピック python -m tablecheck_watcher check
```

## トラブルシューティング

- **「チェックが失敗しています」の通知が来た**:
  TableCheck 側の仕様変更の可能性があります。
  **Actions → probe-tablecheck-api → Run workflow** を実行すると、
  現在のAPIの応答がログに出るので原因調査に使えます。
- **通知が多すぎる/少なすぎる**: `config.toml` の `time_ranges` や `dates` で絞り込めます。

## 注意事項

- TableCheck の公開ドキュメントにない内部APIを利用しているため、
  サイトの仕様変更で動かなくなることがあります (その場合は警告通知が届きます)。
- チェック間隔は10分ごと・1回あたり10リクエスト程度と、
  通常のブラウザ利用と同程度の負荷に抑えています。間隔を極端に短くするのは避けてください。
- 空席の確保 (自動予約) は行いません。通知が来たら手動で予約してください。
